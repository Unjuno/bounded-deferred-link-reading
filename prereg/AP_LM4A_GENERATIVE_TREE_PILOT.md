# AP-LM4A preregistration — frozen generative answer-tree development pilot

Date: 2026-08-27 JST

## Purpose

Test whether the AP-LM3B recursive downstream-value advantage survives when answers and follow-up questions are produced by an actual generative language model rather than by retrieval-backed Wikipedia bodies and graph links.

This is a DEVELOPMENT PILOT only. It may choose a budget/design for a later fresh confirmation. It must not evaluate the final 40% target partition.

## Construct boundary

This experiment tests query scheduling over a frozen tree generated by an LM. It does not yet test factual reliability, human comprehension, or measured API latency. Semantic alignment to a target article is the utility surrogate.

## Generator

- model: `Qwen/Qwen2.5-0.5B-Instruct`
- decoding: deterministic greedy decoding (`do_sample=False`)
- maximum new tokens: 112
- generation prompt contains the current query only; it MUST NOT contain the mission target title or target article text
- format requested from the model:
  - `ANSWER: ...`
  - `Q1: ...`
  - `Q2: ...`
- each answer should be concise; each follow-up should be a short prerequisite/mechanism/related-concept question
- malformed generations retain the answer if recoverable and expose zero or fewer children rather than being regenerated with a different prompt

The generated tree is built and frozen before any scheduling policy is fitted or evaluated. Thus generator randomness/policy choice cannot interact within this pilot.

## Data and missions

Use the existing Wikispeedia corpus and target-disjoint partition logic.

- seed: 20260920
- target partition: 40% fit / 20% development pilot / 40% untouched confirm reserve
- fit missions: up to 32
- pilot missions: up to 24
- confirm reserve: NOT generated, NOT scored, NOT evaluated
- initial roots per mission: 3 visible outgoing article-title queries chosen using the existing visible anchor/title-to-target-title ranking
- maximum generated depth: 2 (root depth 0 plus two generated follow-up levels)
- maximum children per queried node: 2
- maximum nodes per mission: 9

## Query and cost visibility

A candidate query is visible before execution. Its cost is computed only from its visible question text:

`cost(q) = clip(1 + floor((word_count(q)-1)/4), 1, 4)`

No answer length, answer embedding, answer reward, future children, or target article body is available before the query is executed.

## Utility

After a query is executed, its generated answer receives

`reward = max(0, cosine(embedding(answer), embedding(target_article_body)))^2`.

Embedding model: `sentence-transformers/all-MiniLM-L6-v2`.

This reward measures target-semantic alignment, not factual correctness.

## Budgets

Evaluate B=8 and B=12.

## Policies

1. visible greedy: query-target-title cosine per visible query cost
2. matched immediate teacher: Ridge(alpha=10) trained to predict the node's immediate reward
3. matched recursive teacher: Ridge(alpha=10) trained to predict exact frozen-subtree value under the remaining budget
4. recursive K=4 and K=8 frontier compression as exploratory resource audits

Immediate and recursive models use the SAME visible feature vector and the SAME training rows; only the teacher label differs.

Visible features:
- query-to-target-title cosine
- log query cost
- depth fraction
- observed parent reward (zero for roots)
- remaining-budget fraction
- log frontier size
- query-score / cost
- current visible rank fraction

No unqueried answer text or future-child information enters these features.

## Primary development comparisons

For each budget:
- recursive full vs matched immediate
- recursive full vs visible greedy

Use paired target-cluster bootstrap CIs and 8 deterministic target buckets.

## Development gate

A budget is `PROMISING` only if all hold:

- pilot has at least 15 evaluable missions
- generation parse success >= 85%
- mean generated nodes >= 4
- recursive-minus-immediate mean > 0
- recursive-minus-immediate target-cluster 95% CI lower bound > 0
- recursive-minus-greedy mean > 0
- at least 5/8 target buckets are positive for recursive vs immediate

No confirmatory claim is made from this gate.

## Diagnostics

Report:
- generation parse success
- generated-node count and depth distribution
- mean query cost
- reward distribution
- exact oracle value
- policy/oracle fractions
- K=4/K=8 gap to recursive full
- fraction of generated prompts that contain the target title (must be 0 by construction/assertion)

## Invalidating implementation error

The pilot is invalid and must be rerun before interpretation if any of these occur:
- target title/body is included in an LM generation prompt
- an unqueried answer or future child is used as a policy feature
- policy choice changes which tree is generated
- confirm-reserve targets are generated or evaluated

## Next-step rule

- If at least one budget is PROMISING, freeze that budget (prefer the smaller budget if both qualify) and preregister a larger target-disjoint confirmation before generating confirm-reserve trees.
- If no budget is promising but recursive point estimates are positive, inspect generation/parser/feature diagnostics on development data only.
- If recursive is non-positive, do not run confirmation; revise the generative construct on a new development split.
